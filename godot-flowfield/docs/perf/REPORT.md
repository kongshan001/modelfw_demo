| 分辨率 | 初版 B：AA on / 15Hz / 全拖尾 | 默认 ALL：AA off / 10Hz / 半采样 | 绝对中位提升 | 同轮归一提升 | P95 帧时间 B → ALL |
| --- | ---: | ---: | ---: | ---: | ---: |
| 1280×720 | 11.0 FPS [9.5–12.7] | 26.4 FPS [17.0–32.2] | 2.4× | 2.17× [1.37–3.02] | 145.4 → 57.9 ms |
| 1920×1080 | 8.6 FPS [4.7–10.2] | 16.8 FPS [13.7–23.4] | 2.0× | 2.17× [1.55–2.93] | 181.1 → 129.2 ms |

> 括号为 5 轮的最小–最大；同轮归一 = 每轮内该配置相对同轮 baseline 的倍数，用来抵消跨轮机器负载漂移。  
> **本机在复测期间同时运行飞书、浏览器、Godot 编辑器和其他 worker，load1 5.23–24.68（中位 9.34），swap 已用约 4.3–4.5 GB。绝对 FPS 不能与 T-009 的单次 47.0 直接对比；本报告以同轮相对增益、确定性的引擎计数和 5 轮中位/范围为准。**

**每项优化的独立增益（1000 智能体，同轮归一中位倍数）：**

| 因子 | 1280×720 | 1920×1080 | 机制 |
| --- | ---: | ---: | --- |
| 关闭拖尾抗锯齿（AA off） | **1.65×** [0.84–2.33] | **1.46×** [1.35–2.08] | 每条拖尾线段从 AA 多重图元降为 1 条普通线；引擎 objects/primitives 约减半 |
| 拖尾半采样（>700，隔一取样） | **1.25×** [0.74–1.62] | **1.35×** [1.00–2.42] | 拖尾段数 5000 → 2500，几何/填充成本减半 |
| 大群 10Hz 刷新（方向/分离/拖尾） | **1.13×** [0.66–1.40] | **1.22×** [1.06–1.53] | 逻辑步长中位约 −12%（720）/ −26%（1080），更多 CPU 余量；帧渲染受限时 FPS 增幅有限 |
| 三项全开 | **2.17×** [1.37–3.02] | **2.17×** [1.55–2.93] | 近似可加（单项乘积 2.33×） |

**其他关键结论：**

1. **拖尾 AA 是最大单因**：1000 智能体、1280×720 下，AA 开→关使 objects 从 138,088 降到 58,087、primitives 从 151,438 降到 71,436（约 −80k/−80k），中位 FPS 11.0→15.7。说明 `draw_multiline(..., antialiased=true)` 把 5,000 条拖尾线段展开成大量屏幕空间图元，是 T-008 初版的主要瓶颈。
2. **半采样在 AA 关闭后才充分显现**：仅半采样 +28%；先关 AA 再开半采样，中位 15.7→26.9 FPS（+71%）。拖尾段数减半只有在 AA 巨型图元消失后才会成为主要矛盾。
3. **10Hz 主要买 CPU 余量**：逻辑步长中位 18.28→16.17 ms（720，预算 55%→48%），22.84→16.92 ms（1080，68%→51%）；但帧渲染受限时 FPS 只小幅提升（同轮 1.13×/1.22×）。这正是设计意图：移动仍 30Hz，方向/分离/拖尾低频刷新。
4. **500 对照验证阈值逻辑**：500 智能体时半采样/10Hz 不生效（阈值 >700）。500 档 baseline 26.0 FPS、关 AA 40.7 FPS（+56%）、仅半采样 27.1 FPS（在噪声内）、关 AA+半采样 42.6 FPS。半采样与“仅关 AA”的差异证明阈值按预期工作。
5. **剩余最大渲染项不是拖尾，而是流场箭头**：在默认全优化配置下，隐藏箭头层（1000 智能体，1280）中位 26.9→54.4 FPS（+27.5），primitives 66,436→21,400；隐藏智能体+拖尾 +6.8 FPS；隐藏拖尾仅 −0.7 FPS（噪声内）。箭头是 835 格 × 3 段、且使用 AA 的 `draw_multiline_colors`，约贡献 45k primitives。**本轮不改默认视觉，仅记录为后续优化项。**
6. **hitch 仍显著**：1280 初版 1500/1500 帧 >33.3 ms（100%）、100% >50 ms；默认 56% >33.3 ms、26% >50 ms。1080 默认 74% >33.3 ms。负载尖峰造成 0.5–1.5 s 的 worst frame（OS/换页级停顿），因此本报告同时给出“每轮 P95 中位”和“合并 1500 帧分布”，后者对负载尖峰更敏感。
7. **GPU time 在本机不可得**：GL Compatibility 不暴露 GPU 计时器；RenderDoc 未安装且不支持 macOS；Xcode GPU Capture 仅支持 Metal，无法捕获 OpenGL 路径。替代方案见 §6：图层隔离 + RenderingServer 计数 + 同轮归一。
8. **默认行为/视觉未变**：三个优化开关只新增 bench 可调字段，默认值保持 T-009 行为；smoke、headless、旧 bench 与 1920×1080 默认截图回归均通过（§8）。

## 2. 方法

### 2.1 场景与采样

- 场景：`scenes/main.tscn`；地图 `medium`（36×24），样例 C 形回廊，种子 **421**；视图 `flow`，网格/箭头/拖尾/智能体开、数值关（即主场景默认视觉）。
- 主档：**1000 智能体**；对照：**500 智能体**（验证 >700 阈值）。
- 每配置每轮：**60 帧预热 + 300 帧采样**；轮间 15 帧 settle；**5 轮独立运行**（重新 `load_sample()` + `set_agent_count()`，RNG 固定种子）。
- 配置顺序：轮次主序（round-major），每轮把配置顺序**循环左移一位**，避免同一配置总在同一负载位置；至少 5 个配置各领一次“轮首”。
- 垂直同步关闭（`VSYNC_DISABLED`），`Engine.max_fps = 0`；窗口 `ALWAYS_ON_TOP` + `move_to_foreground()`。
- **1280×720**：真实 1280×720 窗口，`project.godot` 的 `canvas_items` 拉伸。
- **1920×1080**：本机屏幕 1440×900；实测请求 1920×1080 时 macOS 把窗口夹成 1440×762，因此使用 **1920×1080 离屏 SubViewport**（`size_2d_override = 1280×720` + stretch，等价 `canvas_items`）。场景以完整 1920×1080 渲染；**present/blit 到屏幕的成本不计入**。保存的 1920×1080 PNG 验证了内容与分辨率。
- 窗口在复测中未获得焦点（前台的飞书在另一个 Space）；`DisplayServer.window_is_focused()` 为 false。渲染计数随配置变化、帧时间随负载变化，说明渲染路径有效；但 macOS 的后台/遮挡窗口策略可能影响绝对值，见 §7。

### 2.2 指标定义

| 指标 | 定义 |
| --- | --- |
| avg FPS | 300 帧间隔之和 → `300 / elapsed_s` |
| P50/P95/P99 | 300 个帧间隔的最近秩百分位（nearest-rank） |
| worst | 300 个帧间隔最大值 |
| hitch >33.3 / >50 | 帧间隔严格大于 33.3 ms / 50 ms 的帧数（每轮 /300） |
| 逻辑步长 | 采样段内 `step_fixed()` 的精确 `step_total_usec / step_count`；预热后清零 |
| 逻辑预算 | 逻辑步长 / 33.33 ms（30Hz 固定步长） |
| 建场时间 | `sim.build_ms()`，最后一次 `_rebuild_field()` 的耗时 |
| 引擎计数 | `RenderingServer.get_rendering_info()` 的 draw calls / objects / primitives；同时记录 `Performance.RENDER_TOTAL_*` 交叉校验（数值一致） |
| 显存 | RenderingServer 的 video/texture/buffer memory（MB） |
| 负载/热 | 每轮 `sysctl -n vm.loadavg` 的 load1/load5；`pmset -g therm` 的 CPU_Speed_Limit |

### 2.3 消融矩阵

`B` = 初版行为 = 拖尾 AA 开 + 每 2 拍刷新（15Hz）+ 全部拖尾。每项优化单独打开/关闭；1000 档跑完整 2×2×2 因子矩阵。

| ID | 拖尾 AA | 大群 10Hz | 拖尾半采样 | 说明 |
| --- | --- | --- | --- | --- |
| baseline (`B`) | on | off | off | 初版行为 |
| aa_off (`-AA`) | **off** | off | off | 仅关 AA |
| hz10 (`10Hz`) | on | **on** | off | 仅 10Hz |
| half (`1/2`) | on | off | **on** | 仅半采样 |
| aa_off_hz10 (`-AA+10Hz`) | off | on | off | 交互 |
| aa_off_half (`-AA+1/2`) | off | off | on | 交互 |
| hz10_half (`10Hz+1/2`) | on | on | on | 交互 |
| all (`ALL`) | off | on | on | 当前主场景默认 |

500 档（10Hz 阈值不生效）只跑 4 组：`B`、`-AA`、`1/2`、`-AA+1/2`。  
图层隔离（仅 1280，默认全优化，3 轮）：all layers、trails off、agents+trails off、arrows off。

### 2.4 方法学说明

- **不全报“最好一轮”**：每项给 5 轮中位 + 最小–最大；原始 CSV 保留每轮，JSON 保留每帧（1000 档与图层档）。
- **跨轮负载漂移**：本机在复测期间被其他任务严重占用。除绝对中位外，另计算**同轮归一**（每轮内配置 FPS / 同轮 baseline FPS；P95 同理），这是本报告的主要因果证据。单因子/组合的“绝对配对”表受不同轮负载影响，只作方向参考。
- **主效应**：每个因子两个水平各汇总 4 种组合 × 5 轮（20 次运行）后的中位，进一步降低单轮尖峰影响。
- **帧级池化**：把 5 轮 × 300 帧合在一起算 P50/P95/P99/hitch，给出真实分布；它包含负载尖峰，故与“每轮 P95 的中位”不同，两者都报告。
- **轮次漂移**：每轮 8 个配置的中位 FPS 与 load1 并排，直接展示负载与帧率的相关性。

### 4.4 解读

- **AA（最大因子）**：5,000 条拖尾线段在 AA 开启时展开为大量屏幕空间图元；objects/primitives 从 138k/151k 降到 58k/71k（−58%/−53%）。在 1080 的同轮归一为 1.46×，虽然低于 720 的 1.65×，但 P95 改善更大（181→109 ms），因为 1080 的填充成本更高。AA 的收益是“少画 + 少几何 + 少填充”三合一。
- **半采样**：5000→2500 段，AA 开时 objects/primitives 减 40k/40k；AA 关时只减 5k/5k。因此“仅半采样”+28%，而在 AA 关掉后 +71%（15.7→26.9）。半采样和 AA 存在明显正交互：两者都在削拖尾几何，先削掉更贵的那层（AA）收益更大。
- **10Hz**：不改变图元数，改变刷新频率。逻辑步长中位 18.28→16.17 ms（720）、22.84→16.92 ms（1080），预算 55%→48% / 68%→51%。FPS 同轮 1.13×/1.22×，小于 AA/半采样；它主要降低 CPU 压力、给 worst frame 留余量，而不是直接提高渲染帧率。
- **组合**：单项同轮倍数乘积 1.65×1.13×1.25 ≈ 2.33×，实测 ALL 2.17×（720）/2.17×（1080）；接近可加，略低于乘积（交互/噪声）。绝对中位比 26.4/11.0 = 2.4× 与同轮归一 2.17× 不同：前者是“两个中位数之比”，后者是“每轮比值的中位”，对轮级负载的配对更稳健（两配置的 load1 中位接近：8.02 vs 8.80）。以同轮归一为主，绝对中位比只作旁证。
- **与 T-009 的单次数据**：T-009 记 1000 默认 47.0 FPS（单次，机器较空）；本次 ALL 中位 26.4 [17.0–32.2]。差异主要来自外部负载与内存压力，而非代码变化：旧 bench 复跑（默认配置）本次 1000 档 32.2 FPS，正好落在本次 ALL 的范围内；500 档 43.3 FPS 与本次 `-AA+1/2` 42.6 吻合。绝对数值不具跨环境可比性，**相对增益与机制结论可复现**。

## 5. 归因

| 观察 | 证据 | 结论 |
| --- | --- | --- |
| 拖尾 AA 是初版的主要瓶颈 | objects 138,088→58,087；primitives 151,438→71,436；仅关 AA 同轮 1.65×/1.46× | AA 线段被展开为屏空间图元，几何+填充双重成本 |
| 半采样只在 AA 关闭后充分显现 | 仅半采样 +28%；AA 关后 +71%；段数 5000→2500 | 与 AA 同为拖尾几何成本，存在正交互 |
| 10Hz 主要降 CPU | 逻辑步长 −12%~−26%；图元数不变；FPS 同轮 1.13×/1.22× | 买的是逻辑预算，不是直接帧率 |
| 箭头层是剩余最大渲染项 | 隐藏箭头 +27.5 FPS（26.9→54.4），primitives −45,036；draw calls 仅 −3 | 835 格 × 3 段 AA 线；不是 draw call 问题，而是图元/填充 |
| 智能体层有 CPU 成本 | 隐藏 agents+trails +6.8 FPS，primitives 只 −4,000 | 每帧 2×1000 次 MultiMesh transform/color 更新被省掉 |
| 拖尾层在默认配置下接近免费 | 隐藏拖尾 −0.7 FPS（噪声内），primitives −5,000 | 半采样+关 AA 后拖尾已不是瓶颈 |
| 分辨率影响是填充/带宽 | 720 与 1080 的 objects/primitives 完全相同；1080 baseline P95 181 vs 720 145；ALL 1080 P95 129 vs 720 58 | 内容提交相同，差异在像素填充；1080 下 ALL 的绝对值还受更高负载影响 |
| 默认仍有 hitches | 720 ALL 56% >33.3 ms；1080 ALL 74%；worst 218/428 ms | 外部负载尖峰 + 箭头/智能体渲染；不是单一优化能解决 |

**当前流水线的成本排序（默认全优化，1280×720，1000 智能体）**：箭头层 ≫ 智能体层（含 CPU 更新）> 拖尾层 ≈ 背景网格/UI。拖尾三项优化已把拖尾从 T-008 的主瓶颈降为接近免费；下一步若还要提帧率，应评审箭头层的 AA/密度/缓存策略（属于视觉/玩法变更，本轮不做）。

## 6. GPU 计时与捕获可用性

| 项目 | 本机状态 | 说明 |
| --- | --- | --- |
| GPU time（RenderingServer / Performance） | **不可得** | GL Compatibility（OpenGL 4.1）不提供 GPU 计时器；`Performance` 无 GPU time 字段。只报告 CPU 侧逻辑步长与帧间隔 |
| RenderingServer 计数 | **可用** | draw calls / objects / primitives / video-texture-buffer memory；与 `Performance.RENDER_TOTAL_*` 逐轮一致 |
| RenderDoc | **不可用** | `renderdoccmd` / `qrenderdoc` 未安装；RenderDoc 官方不支持 macOS 宿主（仅 Windows/Linux/Android 等） |
| Xcode GPU Capture | **不适用** | `xcrun xctrace` 存在，但 GPU Capture / Metal Frame Debugger 只支持 Metal；本项目 `renderer/rendering_method = gl_compatibility`，OpenGL 路径无法被 Metal 工具捕获。`xctrace` 可做 CPU Time Profiler，但回答不了“GPU 花了多少” |
| 替代方案（本报告采用） | **图层隔离** | 在默认全优化配置下依次隐藏 trails / agents+trails / arrows，比较 FPS、P95 与 primitives/objects；配合同轮归一与 5 轮中位，可分解“哪一层贵、贵在几何还是 CPU”。局限：不能给硬件时间戳，且隐藏 agents 同时省掉 CPU 更新，GPU/CPU 归因需结合计数解读 |

若后续必须拿 GPU 时间：可临时切换至 Mobile/Vulkan 渲染器做一次对照捕获（会改变渲染路径，不可与本报告数值混用），或用支持 macOS 的外部 GPU 工具（当前机器/系统均不具备）。

## 7. 方差与局限

1. **机器负载是最大方差源**：复测期间飞书、WebKit、Godot 编辑器（已运行 11 天）和另外两个 worker（T-010 文档、T-013 Duelyst）同时活动。load1 5.23–24.68（中位 9.34），swap 已用约 4.3–4.5 GB（总 5 GB），`kernel_task`/WindowServer 也占用 CPU。帧时间出现 0.5–1.5 s 的 worst frame，属 OS/换页级停顿，不是游戏逻辑单帧卡顿。
2. **720 与 1080 不是同一负载窗口**：1080 各轮 load1 中位 10.2–15.9，720 为 7.5–14.3；1080 还发生在 T-013 启动之后。**不要用 1080/720 的绝对 FPS 比值推断“分辨率成本”**；同轮归一与相同的引擎计数才是可比的。
3. **绝对 FPS 不可与 T-009 对比**：T-009 的 47.0 是较空机器上的单次采样；本次 ALL 中位 26.4（范围 17.0–32.2）。旧 bench 本次复跑 1000 档 32.2、500 档 43.3，说明代码路径一致，差异来自环境。审计结论以相对增益为准。
4. **无 GPU 计时器**：§6。归因是“计数 + 图层差 + 同轮归一”的间接推断，不能给出 GPU ms 分解。
5. **1080 为离屏 SubViewport**：屏幕 1440×900，macOS 把 1920×1080 窗口夹到 1440×762；离屏 1920×1080 渲染包含完整着色/填充，但 **present/blit 成本不计**。真实 1080p 显示器上的绝对值可能略有不同。
6. **窗口未获得焦点**：`window_is_focused() = false`（前台是飞书）。始终置顶、渲染计数正常、帧时间随配置变化，但 macOS 可能对后台/遮挡窗口做节流；仅影响绝对值，不影响同轮相对比较。
7. **5 轮不足以消除长时尖峰**：轮次漂移表显示 load1 可在一轮内到 21+；中位数稳健，但范围会保留这些尖峰。不要只引用最好一轮。
8. **轮首冷启动**：每轮第一个配置可能承担一次性的 shader/font/纹理成本；15 帧 settle + 60 帧预热降低影响，循环轮转把“轮首”分摊到 5 个配置。未领到轮首的 3 个配置可能略占便宜，中位可部分抵消。
9. **单场景/单地图**：medium/421，1000 与 500 两档；未扫 small/large、随机地图、不同目标数、暂停/重置、录制模式。
10. **UI 包含在负载内**：场景默认带右侧 UI 与 HUD 文本；这与玩家真实运行一致，但不是纯模拟微基准。
11. **热状态**：`pmset -g therm` 的 `CPU_Speed_Limit = 100`，无记录的 thermal/performance warning；但 2015 款 15W i7 + 核显在长时间负载下可能降频，未能取得逐轮频率。
12. **数据写入**：每轮后写 CSV/JSON（约 0.5 MB），位于采样窗口之外，并有 settle/warmup 覆盖；对结果影响可忽略。

## 10. 后续建议

1. **箭头层专项（优先级最高，但属视觉变更）**：默认配置下箭头层约 45k primitives、隐藏后 +27.5 FPS（1280，1000 智能体）。可选方案：大群时关闭箭头 AA、按格隔一画箭头、或把静态箭头烘焙成一张纹理。需美术/策划评审，因为会改变默认视觉；本轮未动。用户当前已经可以在 UI 里手动关闭“箭头”获得类似收益。
2. **在空闲机器上补一次绝对基线**：本报告的相对结论稳定，但绝对 FPS 被外部负载压低。T-009 的 47 FPS 与本报告的 26.4 中位不应混用；建议在机器空闲（load1 < 2、swap 稳定）时用同一 `run_ablation.sh` 复跑，补齐“干净环境”一列。
3. **GPU 计时**：如需硬件 GPU ms，临时用 Mobile/Vulkan 渲染器做对照捕获，或换支持 macOS 的外部工具；不要与 GL Compatibility 的数值混表。
4. **10Hz / 半采样保持默认开启**：方向为正，10Hz 显著降逻辑预算，半采样在 AA 关闭后收益明显；无需回退。
5. **增量 BFS**（既有待办）：编辑地图时整场重建 6–14 ms（本机负载下 10–20 ms），与本次渲染优化正交。
6. **把 bench 纳入回归门禁**：建议阈值用“同轮归一”而非绝对 FPS（例如 ALL/baseline ≥ 1.8×，P95/baseline ≤ 0.7），以抵抗共享机器的负载漂移。
