## 1. 等轴地图是“左手投影”，直接把物理 RT 相机拼进去会得到假 Δ

等轴地图用 `sx = (x − y)`，这等价于在 `+x+y` 侧观察后再把 screen-x 镜像。真实透视相机放在 `+x+y` 时，世界 +x 在屏幕上向左；地图上向右。第一版 PoC 直接拿 RT 相机投影 + 精灵脚底锚点拼进地图，同一武器尖的 `A_rt` 与 `A_map` 差了 **145px**，看起来像“相机校准极难”。

把 RT 投影的 screen-x 镜像后（`sx = RT/2 − dot(d,right)/z·f`），同一姿态 Δ 回到 **10.5px**，量级与“方位差 ~10° + 弱透视”一致。

**做法**：跨相机校准前，先用一根骨骼 marker 同时过两条链投影，检查方向符号；不要拿 100px+ 的 Δ 直接去调校准参数，那是在给坐标系 bug 打补丁。

## 2. headless Chromium 首次 `canvas.toDataURL` 可能是空的

首次读回发生在 canvas 首次呈现之前时，返回全透明 PNG（960×540 只有几 KB），但 `getImageData` 可能正常、也没有 console error。结果：GIF 第一帧白屏，或调色板被带偏、文件变小。

**做法**：截帧工具把“PNG < 20KB”视为空帧，重渲染重试（最多 6 次），并先做一次预热读回。加 guard 后重跑，得到的 GIF 与首轮 sha256 完全一致——说明渲染本身是确定性的，问题只在读回时序。

## 3. 可复现的 GIF 管线

- 页面只暴露 `GIFLAB.seek(mode, t)`：所有姿态/拖尾采样都是 t 的解析函数，不依赖 RAF 或真实时钟 → 帧可重放。
- 截帧用 `canvas.toDataURL`（960×540 后备缓冲），不要用元素截图（CSS 会把 960 缩成 958）。
- `ffmpeg` palettegen 128 色 + bayer；96 帧 4s 的 960×540 GIF 约 0.8–1.2MB。
- 循环检查：比较第 95→0 帧差与相邻帧差（本次 0.63–1.01×），同量级即无明显接缝。
