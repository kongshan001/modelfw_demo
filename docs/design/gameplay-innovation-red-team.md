### 0.1 最硬的 5 个问题

1. **P0 · C1 的核心卖点已在交付代码里。** `player.gd:583 try_lamp_break()`、`main.gd:838 extinguish_duration()`、`world.gd:942 set_street_lamp()` 已经实现“灯=攻击 + 街灯数改变 Boss 黑暗”；portfolio 仍把“举/掷/灭灯”写成 N4 的新动词。
2. **P0 · F 分与 brief 工期相差 4–12 倍。** A1 写 3–5 天却给 F4；B2/C1 写 5–7 天却给 F3，而 F3 的锚点是“1–3 个月”。同一份文档里“5–7 天”和“1–3 个月”同时成立，fast-track 门槛无法复算。
3. **P1 · 评分规则要求“逐条证据/待实测”，30 行表没有执行。** §1.3 写“每个分数必须能指向证据；没有 playtest 的分数一律标待实测”，但 §2 只有参考模式/风险两列，零个“待实测”标记。
4. **P1 · fast track 的“10 秒演示”没有交付。** 实际视觉证据只有一张 SVG 评分图，没有 top 3 的灰盒/GIF/原型；B2/C1 的 clarity=3，定义是“要试一局”，与“10 秒看懂”冲突。
5. **P1 · Playtest 单臂、无基线，H1 太弱。** “≥4/5 至少一次”可以由好奇/提示触发；kill 要等“2 次迭代”，但 L1 只有 3–7 天。通过线可以在核心假设为假时被满足。

### 0.2 本报告确认成立的部分（避免虚假全面否定）

- **算术成立**：红队用脚本重算 30 行，五项相加全部与总分一致；分布为 15×1、16×6、17×7、18×11、19×5；≥18 共 16 个，无 ≥20。与 T-034 的声明一致（见 §8 附录）。

- **基线系统大体存在**：`battle_core.gd:10-11` 确认 9×5 棋盘；`inventory.gd:3` 确认 6×4 背包；`main.gd:31`/`world.gd:942` 确认 3 盏街灯；`player.gd:583` 确认灯破。问题在“delta 与证据”，不是“完全没有系统”。

## 1. 问题清单（按严重度）

> 每条按“严重度 → 证据 → 期望 vs 实际 → 影响 → 最小修复”写。P0 阻塞 L1 放行；P1 需在 L1 前修复；P2 影响可追溯性/文档一致性。

### P0-1 · C1 的“新动词”与已交付代码冲突，作为 top 3 创新不成立

- **严重度**：P0（阻塞 C1）
- **证据**：
  - `godot-changan-action/scripts/player.gd:583` 已有 `try_lamp_break()`；`ATTACKS["lampbreak"]` 是 Q 键攻击，命中后 Boss 每阶段可被击倒一次（`enemy.gd:912`）。
  - `main.gd:31` 有 `street_lights_lit`；`main.gd:815` 提示“灯数决定他能熄掉多少光”；`main.gd:836` 的 `extinguish_duration()` 直接由街灯数计算 Boss 二阶段黑暗时长；`world.gd:942 set_street_lamp()` 控制 3 盏街灯；`hud.gd:130` 显示“街灯 x/3”。
  - Portfolio §3.3 仍写“新动词：举 / 掷 / 灭灯”，并给 N4；但“灯=武器 / 灯数改变 Boss 战”已经是现有 build 的 P3 差异化（`docs/design/changan-action-remake-spec.md` §2.3）。
- **期望 vs 实际**：
  - 期望：top 3 的核心动词是“项目里还没有的动作/约束”，10 秒演示能展示与现有 build 的差异。
  - 实际：现有 build 已有 Q 灯破 + 3 街灯 + Boss 熄灯；C1 的新增只剩“灯油 / 掷灯 / 敌人光敏”，brief 没有把它们收敛成一个核心动词，也没有证明它们能独立撑起 L1。
- **影响**：按现 brief 做 L1，团队会用一周重新验证已经存在的行为；即使通过，也不能证明“新玩法”成立。C1 的 N4/D4/A4 没有对应证据。
- **最小修复**：把 C1 从 top 3 创新中移除（KILL）；保留为现有灯系统的 P1 深化。若坚持做，重写为“灯油经济 + 敌人光敏 + 掷灯回收”的单一机制，并提交一个现有 build 做不到的 10 秒灰盒 GIF；否则不进入 L1。

### P0-2 · F 分与 brief 的工期相差 4–12 倍，评分门槛不可复现

- **严重度**：P0（阻塞 fast-track / 总分结论）
- **证据**：
  - Portfolio §0.1：A1 L1 3–5 天；B2 5–7 天；C1 5–7 天。
  - Portfolio §1.2：F3 = “1–3 个月，或 1 个新系统”；F4 = “2–4 周 L1”；F5 = “1 周内灰盒可玩”。
  - 实际打分：A1 F4（总 19）、B2 F3（总 19）、C1 F3（总 18）。
  - 同一份文档里，“5–7 天”与“1–3 个月”同时成立；A1 的“3–5 天”按锚点应是 F5；若 A1 F5，则总分 20，不再是“无 ≥20”。
- **期望 vs 实际**：期望 F 分能从 brief 的复用系统/新系统/天数直接复算；实际 F 分像是按“风险感觉”倒推。
- **影响**：门槛（≥20 L1 / 18–19 fast track）和“没有 ≥20”的叙事都依赖这 1 分；F 分不可复现，fast track 就不能作为放行依据。
- **最小修复**：先定义 F 的单位（只算可玩原型，还是含 5×2 playtest + 1 次迭代）；让工程给每个 top 3 一个“人天 + 新系统清单”的估计；按同一口径重算总分并写出计算过程。若 A1=20，明确它进入普通 L1，而不是 fast track。

### P1-1 · 评分规则要求“逐条证据/待实测”，30 行表没有执行

- **严重度**：P1
- **证据**：Portfolio §1.3 写“每个分数必须能指向现有系统/案例/成本证据；没有 playtest 的分数一律标‘待实测’”；但 §2 的 30 行表只有“参考模式 / 风险”两列，没有证据列，也没有任何“待实测”标记（只有 §6 的总体声明）。
- **期望 vs 实际**：期望每个 N/D/C/F/A 有证据或不确定性；实际是单评审者的主观粗分。
- **影响**：novelty/audience 不可复现；下游无法判断哪些分数是事实、哪些是猜测。
- **最小修复**：给每行加“证据/不确定性”列；所有未 playtest 的分数标“待实测”；top 6 由第二评分者盲评，分歧 >1 分必须记录理由。

### P1-2 · fast track 的“10 秒演示”没有交付；C=3 与“10 秒可懂”冲突

- **严重度**：P1
- **证据**：Portfolio §0.1 声称 top 3 全部 fast track；fast-track 条件（§1.3、scorecard §3）要求“10 秒 GIF/演示能展示差异”。实际只有一张 SVG 评分图（`docs/design/gameplay-innovation-portfolio-scorecard.svg`），没有任何 top 3 的灰盒/GIF/原型；B2/C1 的 clarity=3，而 3 分定义是“一句话+一个演示能懂，但要试一局”，不是“10 秒就看懂”。
- **期望 vs 实际**：期望先有 10 秒差异演示再 fast track；实际是先写“fast track”，再假设演示会存在。
- **影响**：fast-track 变成跳过 L0 的通行证；如果演示做不出来，团队会先花 5–7 天做 L1，再发现差异不可感知。
- **最小修复**：每个 top 3 先做 10 秒灰盒 GIF（或 1 天 L0），用 3 名目标玩家盲看；说不清差异就降级/重做。把“C≥4”作为 fast-track 的前置条件，而不是 C=3 也放行。

### P1-3 · B2 的“复用”描述与代码不符，核心反馈在暂停中看不到

- **严重度**：P1（影响 L1 工期与可读性）
- **证据**：
  - Portfolio B2 L1 写“复用 hitscan 弹道”；实际玩家射击是 hitscan（`player.gd:198-215`），但敌方来弹是 projectile：`enemy_bullet.gd:41` 每帧 raycast，`enemy_bullet.gd:49-50` 距离 <15 才 `take_damage`。
  - Portfolio 写“背包界面受击高亮”；实际 `backpack_panel.gd:54` 打开背包即 `get_tree().paused = true`，世界暂停，受击不可能在背包界面实时发生。
  - 玩家碰撞是半径 11 的圆（`player.gd:51-53`），6×4 背包格没有映射到任何身体/受击体积；这是一个新系统，不是复用。
- **期望 vs 实际**：期望 L1 只加“物品耐久 + 2D 投影判定 + 受击高亮”；实际要加“背包格→身体部位映射 + 来弹命中物品 + 暂停外的受击反馈 + 耐久破坏状态”，至少 4 个新件。
- **影响**：5–7 天估计偏乐观；H4“装包 <30 秒/无不知道哪格中弹”在暂停 UI 下无法验证。
- **最小修复**：先做 L0 纸面/2D mock，定义“身体图”与命中反馈；明确暂停策略（改为不暂停，或把受击结算放到关背包后）；让工程按新系统重估；把 F3 保留但把 L1 改为 L0→L1 两段。

### P1-4 · Playtest 单臂、无基线；H1 太弱，kill 太晚

- **严重度**：P1
- **证据**：三个 brief 都是“5 人 × 2 轮”，R1 只玩新机制，没有 vanilla 对照；A1 H1“≥4/5 至少一次为了地形放弃召唤”；B2 H1“≥4/5 至少一次调整背包”；C1 H1“≥4/5 至少一次灭灯/掷灯”。这些“至少一次”可以由好奇/提示触发，不证明取舍成立。H2 是访谈原话，容易迎合；H3“想再来”受社交影响；kill 条件要求“2 次迭代后”，但 L1 只有 3–7 天建原型。
- **期望 vs 实际**：期望证明“新机制改变了选择”，实际只证明“玩家试过新按钮”。
- **影响**：通过线可以在核心假设为假时被满足；团队会误以为机制成立。
- **最小修复**：采用 within-subject A/B（同一玩家先玩 vanilla 再玩机制，顺序平衡；或 5+5 两组），测“在同样局面下是否选择新动词 + 能否说出代价”；H1 改为“≥4/5 在至少 2 个独立回合做出该选择，并说出放弃了什么”；H2 用行为/回放计数，不只访谈；R1 设一个“首 3 分钟 kill 开关”（0/5 做出选择即停），不要等 2 轮。

### P1-5 · A1 的 L1 AI 只覆盖火墙，无法验证“地形是双向的”

- **严重度**：P1
- **证据**：Portfolio A1 L1 只写“AI 一条规则（能绕火墙就绕，不能就硬穿）”；但 A1 的核心主张是“地形对双方生效”（§3.1），而 3 种地形里有草丛（挡视线）和高地（远程+1）。AI 没有规则使用草丛/高地，也没有远程单位重新选目标的逻辑。
- **期望 vs 实际**：期望 AI 至少对 3 种地形有反应；实际只有火墙绕路。H1/H2 可能通过，但只证明“玩家会用火墙”，没有证明“地形是争夺资源”。
- **影响**：A1 的 depth=4 和“双向”卖点未被验证；L1 可能做出一个“玩家单方面受益”的地形系统。
- **最小修复**：在 L1 加两条 AI 规则（草丛：远程单位优先选有视线目标/绕开；高地：优先站高地/远程射程计算）；或者把 L1 明确缩成“火墙一种地形”，同时把“双向”从本轮主张里删掉。测“每局每种地形改变合法动作的次数”，<3 次/局就说明不值得占卡位。

### P1-6 · 30 行 ≠ 30 个不同机制；seed 数量被家族重复放大

- **严重度**：P1
- **证据**：portfolio 自己写了 C5“与 C1 重叠；应合并成一套经济”，C8/C9/C10“作为同一套灯系统的第二波组合，不单独立项”；B6/B10 都是保险，B1/B9 都是声音，A7/A8 都是资源维护。按家族合并约 23 个，不是 30 个。
- **期望 vs 实际**：期望 30 个 seed 覆盖 30 个不同的决策结构；实际是约 23 个家族 + 若干变体。
- **影响**：“30 seeds / 16 ≥18”让 portfolio 看起来比实际更宽；top 3 是从一个更窄的池子里选的。
- **最小修复**：在 §2 加“family”列；报告“30 行 / 约 23 家族 / 首波候选 N 个”；对同一家族的变体只保留 1 个代表，其余标“modifier/second wave”；重排后再看 top 3 是否仍成立。

### P1-7 · C1 的 30 FPS 门槛没有可复现记录；黑暗可读性没有无障碍兜底

- **严重度**：P1
- **证据**：C1 H4 写“≥30 FPS”；portfolio 没有给出测量命令/场景/采样时长/分辨率；项目有 `godot-changan-action/tools/probe_fps.gd`，但 docs 里没有 `CHANGAN_FPS` 的实际输出（搜索 `CHANGAN_FPS` 只命中设计规格里的命令，不是实测）。C1 kill 写“黑暗让 >50% 玩家迷路/挨打不知道为什么”，但没有亮度/对比度/音频提示的无障碍选项。
- **期望 vs 实际**：期望 H4 是可复现的验收项；实际是目标值。
- **影响**：C1 的可行性/受众判断没有性能证据；黑暗可读性风险无法在 playtest 中被公平评估。
- **最小修复**：固定探针命令（1280×720、vsync off、同一场景、30 秒采样、报告 avg/min/median/draw calls）；在 playtest 前提供亮度/对比度/音频提示选项；H4 改为“avg≥30 且 min≥20 且 0 次无解释挨打”。

### P2-1 · Skill 承诺的输出文件没有落地（只有模板）

- **严重度**：P2
- **证据**：`SKILL.md §2.2` 列出的输出包括 `docs/design/gameplay-innovation-scorecard.md`、`gameplay-playtest-plan.md`、`gameplay-taste-rejection.md`；T-034 只在 `docs/templates/` 放了模板，portfolio 内联了内容，`docs/design/` 没有这三个文件。
- **期望 vs 实际**：期望下游能直接拿填好的 scorecard/playtest/rejection；实际要读 portfolio 再抄模板。
- **影响**：决策记录不可追溯；下一个角色不知道哪版是“当前结论”。
- **最小修复**：要么补三个填好的文件（top 3 的 scorecard、playtest 记录、rejection log），要么改 skill 的输出契约，明确“模板 + portfolio 内联”是允许的。

### P2-2 · 项目事实小错：20 张牌 vs 16 张卡池；C1 的“现有灯笼/光照”只对了一半

- **严重度**：P2
- **证据**：A1 L1 写“20 张牌中的基础随从”；README 明确“每套 20 张，卡池 16 张（12 随从+4 法术）”。C1 L1 写“复用现有灯笼资产/光照”；实际玩家腰间只有 `_lamp_glow` 发光网格（`player.gd:206-220`），`_lamp_light: OmniLight3D` 声明了但从未实例化；真正的光来自 3 盏街灯（`world.gd:920/942`）和 cam_key。
- **期望 vs 实际**：期望“复用”清单精确到节点/系统；实际混用了“资产存在”和“功能存在”。
- **影响**：F 分与 L1 范围建立在错误前提上；C1 的“可携带光源”其实是新做。
- **最小修复**：加一张“现有/要新建”表；把 20 张套牌与 16 张卡池分开写；C1 明确“玩家灯是发光道具，不是光源；可携带光要新建”。

### P2-3 · C1 playtest 样本偏向硬核，和“动作轻中度”目标不一致

- **严重度**：P2
- **证据**：C1 目标玩家写“动作轻中度（Sifu/如龙/热血无赖一类）”；playtest 却招“3 名动作游戏核心 + 1 名氛围/国风 + 1 名新人”。Sifu 本身偏硬核，核心玩家可能更喜欢“更黑更难”，不能代表轻中度。
- **期望 vs 实际**：期望至少 2 名陌生目标玩家（模板 §3）；实际 3 名核心。
- **影响**：audience fit=4 没有证据；playtest 可能高估 depth、低估 clarity。
- **最小修复**：按 2 轻中度 + 1 新人 + 2 核心招募；按人群分段报告；C1 的 A 分标“待实测”，不要先写 4。

### P2-4 · 5 人样本的“≥4/5”被当成硬门槛，统计上分不清 3/5 和 4/5

- **严重度**：P2
- **证据**：5 人单臂；4/5 的 95% Wilson 区间约 [0.38, 0.99]，3/5 约 [0.19, 0.81]；两者大幅重叠。报告仍把“≥4/5”写成通过线。
- **期望 vs 实际**：期望用 5 人做方向性判断；实际把方向性判断写成二元门槛。
- **影响**：假阳性/假阴性都会发生；团队可能因为 4/5 通过一个实际只有 3/5 的机制。
- **最小修复**：报告原始计数 + 区间；把 5 人当“筛掉明显不行”，不当作“证明成立”；关键假设用 within-subject 行为差，而不是人数门槛。

### P2-5 · 资产许可清单没有进入 top 3 的 L1 范围

- **严重度**：P2
- **证据**：top 3 的“复用”包括现有资产；portfolio 的 IP 段只写“不复制”，没有列出 L1 会用到哪些外部资产/许可（例如项目里已有的 CC0 资产）。L1 虽然用灰盒，但“复用现有资产”需要逐个登记来源/许可。
- **期望 vs 实际**：期望 L1 前有 asset license checklist；实际只有一句“原创/CC0”。
- **影响**：如果后续把 L1 截图/录屏外发，可能把许可不明的资产带出去。
- **最小修复**：在 brief 的 IP 段加“L1 资产清单（来源/许可/是否可商用）”；灰盒优先用色块/图标，不引入新外部资产。

## 2. 方法论攻击

### 2.1 五项评分：有定义，但没有“可复现”

**成立的部分**：五项有 1/3/5 锚点，2/4 插值，门槛与 T-033 一致；总分 = 五项相加；加权公式算得对（红队复算 A1=3.90、B2=3.85、C1=3.60，与文档一致）。这比“只写形容词”的评审强。

**不成立的部分**：

- **单评审者、无校准**：30 个分数由同一作者给出；没有第二评分者、没有评分者间一致性、没有盲评。`SKILL.md` 自己说“实现者自评无效”，但 portfolio 的评分仍是设计者自评，T-035 之前没有任何独立分数。
- **没有逐条证据**：§1.3 要求“每个分数必须能指向现有系统/案例/成本证据”，但 §2 的表没有证据列；只有“风险”列。N/D/C/F/A 的具体理由不可追溯。
- **没有“待实测”标记**：§1.3 要求“没有 playtest 的分数一律标待实测”，但 30 行表零标记；只有 §6 的总体声明。按文档自己的规则，这 30 行都不合格。
- **锚点与事实冲突**：F 分与 brief 工期相差 4–12 倍（P0-2）；N5 的锚点是“改写品类契约”，B2 并没有改写“搜打撤”的契约（搜、打、撤不变），只是改了伤害结算；N5 至少应降为 N4。C1 的 N4 与现有代码冲突（P0-1）。
- **加权与未加权双轨**：门槛用未加权总分，选择逻辑又用“novelty ≥4 + 三项目各一”；加权分只在同分时参考。C1 的加权 3.60 低于 C8 的 3.65、C9 的 3.75，但仍进 top 3，因为“三项目各一”。这个多项目约束是合理的，但应写明“portfolio 约束优先于加权排名”，否则读者会以为 top 3 是分数最高的三个。
- **“无 ≥20”是 1 分 artifact**：A1 若按锚点 F5，总分 20；B2/C1 若 F5/F4，总分 21/20 或 20/19。也就是说，“无 ≥20、全部 fast track”不是稳定结论，而是 F 分口径的产物。用 19 vs 20 做门槛，必须有 ±1 的不确定性说明。

**最小修复**：

1. 第二评分者盲评 top 6；分歧 >1 分必须写理由。
2. 每个分数加“证据/不确定性”列；未 playtest 的一律标“待实测”。
3. 先定义 F 的单位，再重算；总分表附计算过程。
4. 明确“portfolio 约束（三项目各一）”与“分数排名”的优先级。
5. 对 19/20 边界加 ±1 不确定性；不要用 1 分差做“fast track vs L1”的硬判决。

### 2.2 Novelty 仍然是“看描述”，不是“看感知”

Portfolio 的 novelty 分是设计者对着自己写的一句话打的分，没有经过目标玩家的感知测试。三个 top 3 都有具体的先验作品/机制需要对照：

| ID | 先验作品/机制（只列结构，不列素材） | 需要回答的 delta |
| --- | --- | --- |
| A1 | **Faeria**（Abrakam Entertainment SA，Steam app 397060，2017-03-08）：铺地块改变棋盘/召唤条件；**Duelyst**：小棋盘 + 地块/站位。T-034 自己在 A1 的 IP 段引用了这两个 | “地形牌与随从抢手牌”是否产生 Faeria 没有的取舍？如果只是“把 Faeria 的地块换成卡牌”，N 应为 3，不是 4 |
| B2 | **Escape from Tarkov**：网格背包 + 护甲/部位命中；**Backpack Hero / Backpack Battles**：网格摆放作为构筑；**Receiver 2**：身体部位伤害 | “背包格=受击体积”是否是 1:1 已有？如果不是，delta 是什么？N5 需要“改写品类契约”，而搜打撤契约未变，最多 N4 |
| C1 | **Alan Wake**：光作为武器；**Amnesia: The Dark Descent**：提灯油量/黑暗；**Dying Light**：UV 光对夜行敌人；以及本项目已有的 Q 灯破 + 3 街灯 + Boss 熄灯 | “可携带光 + 敌人光敏 + 灯油”是否只是把已有灯系统加一个油条？如果是，N 应为 2–3，不是 4 |

> 说明：以上是机制级对照，不是法律意见；红队本轮没有做系统 prior-art 检索，也没有做商标检索。Faeria 的 app ID/开发者/发售日已用 Steam store API 核对（397060，Abrakam Entertainment SA，2017-03-08；商店描述含“living board / shape the battlefield”）；其余作品为机制级常识，下一轮必须补 3 个可查证来源（商店页/设计访谈/GDC），并写“取什么/不取什么”。

**可执行的 novelty 测试**：给 3 名目标玩家看 10 秒灰盒 GIF（不带美术/名字），问“这像什么游戏？哪里不一样？”如果 3 人都说不出差异，N≤3；如果 2 人说得出且能复述，N≥4。这个测试比设计者自评更接近“10 秒可感知”的定义，也能直接用于 fast-track 条件。

### 2.3 Feasibility 是“拍脑袋”，不是“工程估计”

- F 分的锚点是时间/系统，但打分没有工程输入：没有“谁做、多少小时、哪些现有代码、哪些新系统”的清单。
- A1 的“3–5 天”与 F4 的“2–4 周”冲突；B2/C1 的“5–7 天”与 F3 的“1–3 个月”冲突（P0-2）。
- “复用”被当成“零成本”：B2 的“复用 hitscan”实际是 projectile（P1-3）；C1 的“复用灯笼/光照”实际玩家灯没有 OmniLight（P2-2）；A1 的“复用 9×5/视线”成立，但地形牌需要新的 cell-target 模式（`battle_core.gd:392-404` 的法术目标只接受单位）。
- 没有“验证成本”：5 人 × 2 轮 playtest、招募、记录、复盘、1 次迭代都不在 3–7 天里。L1 决策周期实际是 2–4 周，不是 1 周。

**最小修复**：做一张 capacity sheet：

| 项 | 内容 |
| --- | --- |
| 现有可复用 | 文件/节点/函数（精确到 `file:line`） |
| 新系统 | 1–3 个；每个的人天 |
| 内容 | 卡/敌人/场景/UI 的数量 |
| 验证 | 5×2 的招募/记录/复盘人天 |
| 总工期 | 构建 + 验证 + 1 次迭代 |
| 风险 | 性能/可读性/AI/许可；触发条件 |

没有这张表，F 分不应进入门槛计算。

### 2.4 Playtest 设计：单臂、弱假设、晚 kill

- **单臂无基线**：R1 只玩新机制，没有 vanilla 对照。玩家说“地形改变了我”，可能只是因为游戏里只有地形；不能归因于机制。
- **H1 太弱**：“至少一次”是“试过”，不是“取舍成立”。一个好奇的玩家点一次新按钮就能满足 4/5。
- **H2 是访谈**：“说得出地形改变了走位”容易被主持人引导；没有行为证据（回放中实际走位变化、选择次数）。
- **H3 是社交**：“想再来一局”在 25 分钟 demo、主持人旁观的情境下会偏高；没有行为 follow-up（是否主动再开一局）。
- **kill 太晚**：“2 次迭代后”意味着 2–3 周、10–15 名玩家；对一个 3–7 天的 L1，应该先设“首 3 分钟 kill 开关”。
- **样本小**：5 人 4/5 与 3/5 的 95% 区间大幅重叠（P2-4）；这不是“证明成立”，是“方向性信号”。

**最小修复（可直接执行）**：

1. **Within-subject A/B**：同一玩家先玩 vanilla 3 分钟，再玩机制 3 分钟，顺序平衡；记录“在相同局面下选了什么、为什么”。或者 5+5 两组，同一关卡/同一 AI seed。
2. **H1 改写**：≥4/5 在至少 2 个独立回合选择新动词，并能说出“我放弃了什么”；不是“至少一次”。
3. **H2 行为化**：用回放计数（例如 A1：地形改变合法移动/攻击的次数；B2：为挡弹调整背包的次数；C1：灭灯/掷灯后敌人行为变化的次数），访谈只作补充。
4. **H3 行为化**：结束后不提示，记录玩家是否主动再开一局；或让玩家在“再来一局/玩另一个 demo”之间选。
5. **R1 kill 开关**：如果 0/5 在首 3 分钟做出目标选择，直接停，不进 R2；不要把“再改一个变量”当成默认。
6. **预注册**：在测试前写死 H1–H4、通过线、kill 线、分析人；不要看到结果再改口径。

### 2.5 Seed 多样性与计数：30 行，约 23 个家族

Portfolio 自己已经承认部分重叠：

- C5 “与 C1 重叠；应合并成一套经济”；C8/C9/C10 “作为同一套灯系统的第二波组合，不单独立项”。
- B6/B10 都是保险；B1/B9 都是声音；A7/A8 都是资源维护。

按家族合并（红队口径）：

| 项目 | 家族数 | 合并示例 | 首波候选（非 L0-only、N≥4、无 ≤2） |
| --- | ---: | --- | --- |
| 卡牌战棋 | 9 | A7+A8 → 资源维护；A2 信息；A1 地形；A3 连通；A4 规则；A5 共享；A6 时间轴；A9 法力银行；A10 诈牌 | A1、A3、A4（A9/A10 偏 L0） |
| 搜打撤 | 8 | B1+B9 → 声音；B6+B10 → 保险；B2 背包；B3 雾；B4 撤离；B5 负担；B7 NPC；B8 契约 | B1、B2、B3、B5、B7（B4/B8 模式） |

### 2.6 文档/输出契约：模板不是交付物

`SKILL.md §2.2` 的输出表要求 `docs/design/gameplay-innovation-scorecard.md`、`gameplay-playtest-plan.md`、`gameplay-taste-rejection.md`；T-034 实际只交付了 `docs/templates/` 下的模板和 portfolio 内联内容。对下游来说，模板没有“本轮分数/证据/决策”，不能替代 scorecard。要么补三个填好的文件，要么把 skill 的输出契约改成“模板 + portfolio 内联”，并在 portfolio 里明确“这是本轮唯一事实源”。

另外，project fact 需要一张“现有/新建”表：A1 的 20 张套牌 vs 16 张卡池；B2 的 hitscan vs projectile；C1 的灯 glow vs OmniLight。把这些写清楚，F 分和 L1 范围才有依据。

## 3. Top 3 对抗评审

> 每节按“先验作品 → 核心动词/约束 → 决策空间/首 10 分钟 → L1 可行性 → playtest/kill → IP/范围 → verdict → 下一轮必须回答”展开。verdict 不是分数，是放行建议。

### 3.1 A1 · 地形即手牌（卡牌战棋）— **KEEP（条件式）**

**先验作品/机制（不是 IP 素材）**

- **Faeria**：铺地块改变棋盘/召唤条件；T-034 在 A1 的 IP 段自己引用了它。
- **Duelyst**：小棋盘战棋 + 地块/站位；T-034 也引用了它。
- 这两者说明“地形牌”不是品类里“没有的新动词”；A1 的潜在 delta 是“地形与随从抢同一份手牌 + 地形影响远程视线”。这个 delta 可能存在，但 brief 没有把它写成一句可检验的差异，也没有 10 秒演示。

**核心动词/约束是否真实**

- 真实：`铺` 是一个新动作；`每回合 1 张、对双方生效、与随从抢手牌` 是清晰约束；“玩家放弃什么”写得出来（这一回合的召唤/站场）。
- 但“铺 / 改造”是两个动词；应明确 **核心动词 = 铺**，改造只是支持。否则会变成功能堆叠。

**决策空间/首 10 分钟**

- 决策存在：地形 vs 召唤；草丛挡视线、火墙逼走位、高地换射程。首 10 分钟的节奏（0–1 教学、1–3 第一次挡远程、3–6 AI 绕火墙、6–10 高地）是合理的。
- 但**没有数值/频率**：
  - 9×5 棋盘上，远程视线只检查距离 2 的中间格（`README` 规则）；草丛只在“远程对距离 2 的目标”时生效。每局能触发几次？如果 <3 次，地形牌不值得占一个手牌位。
  - 火墙只对“经过”的单位造成伤害；高地只对远程单位 +1 射程。三种地形的触发频率差异很大，brief 没有估算。
  - “地形 vs 召唤”的取舍取决于地形牌的费用/节奏；brief 没有给一个 sample turn（手牌、法力、场面），读者无法判断玩家是否真的会纠结。
- **必须补**：一张“每局每种地形改变合法动作的次数”的估算表 + 一个 sample turn（2–3 个选项，为什么难选）。

**L1 可行性**

- 真复用：`battle_core.gd:10-11` 9×5；召唤/移动/攻击/远程视线存在。
- 真新增：现有法术目标只接受单位（`battle_core.gd:392-404` `_valid_spell_target` 先 `find_unit`），地形牌要打空格，需要新的 cell-target 模式 + 棋盘地形层 + 渲染 + AI。这不是“只加 3 张牌”，是“卡牌目标系统 + 棋盘状态 + AI”三处改动。
- AI：L1 只写“能绕火墙就绕，不能就硬穿”；草丛/高地没有 AI 规则。H1/H2 可能通过，但“地形是双向的”没有被验证（P1-5）。
- 3–5 天：如果只做火墙 + 灰盒 + 一条 AI，可能成立；如果要做 3 种地形 + 双向 AI + cell-target，5 天偏紧。让工程按“3 种地形 + 1 条 AI/地形”估一次。

**Playtest / kill**

- H1“≥4/5 至少一次为地形放弃召唤”太弱；应改为“≥4/5 在至少 2 个独立回合选择地形，并能说出放弃了什么”。
- H2 访谈容易被引导；用回放计数（地形改变合法移动/攻击的次数）。
- H4 首操作 ≤60 秒、规则 ≤30 秒：对卡牌战棋老手合理；对新人要把“基础规则”和“地形规则”分开计时。
- kill 条件“2 次迭代后仍把地形当 buff”太晚；R1 就应设“0/5 做出取舍即停/改约束”。

**IP/伦理/范围**

- 无直接 IP 复制；Faeria/Duelyst 是抽象结构参考。风险是“换皮”而不是版权：如果 delta 只是“把 Faeria 的地块做成卡牌”，novelty 应降为 3。
- 名称“草丛/火墙/高地”是通用词；上线前做商标检索即可。
- 范围：A1 是三者中最接近“1 周可灰盒”的；但仍需把“3 种地形”砍到“1 种地形 + 1 条 AI”做首日 L0，再决定是否扩到 3 种。

**Verdict：KEEP（条件式）**

> 允许进入 1 天 L0（纸面/色块），不允许直接进 L1。L0 必须回答：地形触发频率、sample turn 的取舍、AI 对草丛/高地的规则、Faeria delta。若 L0 不能证明“地形 vs 召唤”的取舍，降为 ITERATE；若 delta 只剩“卡牌化地块”，降为 KILL。

**下一轮必须回答**

1. 在 9×5/现有远程规则下，草丛、火墙、高地每局各能改变多少次合法动作？给估算和依据。
2. 给一个 sample turn：手牌、法力、场面、2–3 个选项；玩家为什么难选？
3. AI 如何用草丛/高地，而不只是绕火墙？如果只做火墙，A1 的“双向”主张是否要删？
4. 与 Faeria/Duelyst 的一句话 delta 是什么？10 秒灰盒能展示什么它们没有的东西？

### 3.2 B2 · 背包即护甲（搜打撤）— **ITERATE（先 L0）**

**先验作品/机制（不是 IP 素材）**

- **Escape from Tarkov**：网格背包 + 护甲/部位命中；但 Tarkov 的背包不是“护甲”，护甲是独立装备。
- **Backpack Hero / Backpack Battles**：网格摆放作为构筑/战斗空间；但没有“物品挡子弹”的物理表达。
- **Receiver 2**：身体部位伤害/武器操作；但没有背包格映射。
- 因此“背包格=受击体积”可能是一个新的组合，但不是“品类里没有”的全新动词；N5 的锚点是“改写品类契约”，而 B2 没有改写搜打撤的“搜→打→撤”契约，最多 N4。T-034 自己写“网格背包是通用类型元素”，也支持这个降分。

**核心动词/约束是否真实**

- 动词是 **装包**；“挡弹”是结果/反馈，不是第二个核心动词。brief 把“装包 / 挡弹”并列，容易让工程以为要做两个系统。
- 约束“6×4 格=受击体积”是清晰的；但**受击体积如何映射到俯视角角色**没有定义：
  - 玩家是半径 11 的圆（`player.gd:51-53`），不是人形骨架；
  - 6×4 背包格是 UI 数据（`inventory.gd:3`），没有朝向/身体部位/世界坐标；
  - 敌人子弹是 projectile（`enemy_bullet.gd:41`），不是 hitscan；要挡弹，需要把子弹的命中查询从“圆碰撞”改为“背包格代理体”。
- 这不是“复用弹道”，是“新建一个受击代理系统 + 物品耐久 + 命中反馈”。

**决策空间/首 10 分钟**

- 决策存在：带医疗包/高价值品/留空位；高价值品可能更占格/更脆。首 10 分钟的 0–1 提示、1–3 第一次挡弹、3–6 贪婪代价、6–10 结算是合理的。
- 但关键失败状态没写：
  - 物品耐久归零后，是**碎掉/掉落/只失效**？如果碎掉，玩家会失去战利品（强取舍）；如果不碎，背包就是无限护甲（“清空背包”反而可能是最优）。
  - 子弹打在“背包格”上，玩家看到的是**世界里的角色**还是**背包 UI**？背包打开时世界暂停（`backpack_panel.gd:54`），所以“受击时背包界面高亮”在实时战斗中不可能发生；如果改成不暂停，玩家又要在战斗中看背包，节奏会断。
  - “空白格”是否等于“身体暴露”？如果是，最优策略可能是“把贵重物品放中间、四周留空”？brief 没有说明布局规则。
- **必须补**：一张 6×4 的“身体图”（哪些格对应正面/侧面/背面、哪些格是暴露），一个“耐久归零”规则，一个“暂停/不暂停”的选择，以及一个“清空背包是否最优”的对抗测试。

**L1 可行性**

- 5–7 天：如果只做“4 个方向的简化命中 + 物品耐久 + 受击高亮”，可能成立；但需要：
  1. 新受击代理体（6×4 格 → 世界空间）；
  2. 来弹命中物品的查询；
  3. 耐久/破坏状态；
  4. 暂停外的反馈（世界飘字/音效/角色受击方向）；
  5. 背包 UI 的“哪格被击中”复盘。
- 这是 5 个新件，不是“复用现有背包/弹道”。F3 是合理的；但“5–7 天”需要工程确认，不能由设计者估。
- 建议路径：**L0 纸面/2D mock（0.5–1 天）→ 工程估时 → L1**。L0 只需回答“玩家能否看懂哪格挡了哪颗子弹、是否愿意为挡弹牺牲容量”。

**Playtest / kill**

- H1“≥4/5 至少一次调整背包”太弱；玩家可能为了装更多东西而调整，不是因为挡弹。
- H2“说得出装包策略”容易得到“把医疗包放前面”这类泛泛回答；要用“同一局面下两次选择”的行为证据。
- H4“装包 <30 秒”不是核心；核心是“受击可读性”：玩家能否在死亡回放/结算中说出“哪颗子弹打在哪格、为什么死”。
- kill“最优解永远是清空背包”是对的，但需要在 L0 就测：给玩家“空包/满包/混合”三种预设，问他会选哪个、为什么；如果 4/5 选空包，机制不成立。
- 样本：3 名搜打撤核心 + 1 名射击 + 1 名新人，缺少“轻中度/不玩搜打撤”的目标玩家；至少加 1 名非硬核。

**IP/伦理/范围**

- 无直接 IP 复制；Tarkov/Backpack Hero 是抽象结构参考。风险是“prior art 没查清”导致 N5 虚高，不是版权。
- 伦理：把身体当背包格可能产生“物化身体”的怪异感，但当前是灰盒/俯视 2D，不涉及血腥；保持非血腥表达即可。
- 范围：不做全物理、不做新枪/新敌人/新地图；这些 brief 已经写了。要把“背包 UI 暂停”与“实时受击”二选一说清楚，否则范围会偷偷膨胀。

**Verdict：ITERATE（先 L0）**

> 不允许直接进 L1；先做 0.5–1 天 L0/2D mock，回答“身体图、耐久归零、暂停策略、清空背包是否最优、工程人天”。L0 通过后再进 L1；若 L0 发现玩家看不懂“哪格挡弹”，kill 或改成“护甲板/掩体”这类更可读的表达。

**下一轮必须回答**

1. 6×4 背包格如何映射到俯视角角色的正面/侧面/背面？玩家在世界上看到什么？
2. 背包打开时世界暂停，受击反馈在什么时候、用什么形式出现？如果改成不暂停，战斗节奏如何保持？
3. 物品耐久归零后发生什么？空白格是否等于暴露？“清空背包”为什么不是最优？
4. 工程估计：新受击代理体 + 来弹查询 + 耐久 + 反馈，各多少人天？5–7 天是否包含 L0 和 playtest？

### 3.3 C1 · 灯是武器（3D 动作）— **KILL（作为 top 3 创新；保留为 P1 深化）**

**先验作品/机制（不是 IP 素材）**

- **Alan Wake**：光作为武器，消耗电池/光源；T-033/T-034 自己把 Alan Wake 列为参考抽象结构。
- **Amnesia: The Dark Descent**：提灯油量/黑暗恐惧；**Dying Light**：UV 光对夜行敌人。
- **本项目已有**：Q 灯破（`player.gd:583`）、3 盏街灯（`main.gd:31`/`world.gd:942`）、Boss 二阶段熄灯（`main.gd:827-838`）、HUD“街灯 x/3”（`hud.gd:130`）。
- 因此“灯=武器/光=资源”不是本项目的新动词；C1 的潜在 delta 只有“可携带光 + 敌人光敏 + 灯油 + 掷灯”。这个 delta 可能成立，但当前 brief 把它包装成“举/掷/灭灯”的新动词，和现有 build 冲突。

**核心动词/约束是否真实**

- brief 列了 **3 个新动词**（举 / 掷 / 灭灯），违反 `SKILL.md` 的“1 个核心动词 + 最多 2 个支持动词”。这不是“一个可玩核心”，更像“一个灯系统 + 多个功能”。
- 如果核心动词是“控光”，那么“举/掷/灭”只是操作；brief 应该写“玩家反复决定光落在哪里/照谁”，并给出一个 30 秒循环。
- “掷灯”没有回收规则：灯丢出去后，玩家怎么拿回来？如果拿不回来，玩家可能永远不掷；如果可以回收，回收的代价是什么？brief 没写。
- “灯油”没有经济数字：每秒消耗、点亮街灯消耗、回复方式、上限；没有这些，H2“说得出灯油取舍”无法成立。
- “敌人光敏”没有状态机：亮处后退/暗处靠近的触发半径、冷却、是否会被玩家利用到“卡门口”无伤；brief 没写。

**决策空间/首 10 分钟**

- 决策存在：光 vs 暗、油 vs 安全、点街灯 vs 惊动敌人。首 10 分钟的节奏（0–1 给灯、1–3 逼退/绕后、3–6 点灯 vs 摸黑、6–10 Boss 前 3 盏灯）是合理的。
- 但**首 10 分钟的“Boss 前 3 盏街灯”已经是现有 build 的流程**（`main.gd:751` 任务“点亮三盏街灯”、`main.gd:815` Boss 提示），不是 C1 的新设计。C1 的新内容只有“可携带光/油/掷灯/光敏”，而 brief 没有给一个“现有 build 做不到”的首 10 分钟场景。
- 可能的 dominant strategy：
  - 如果“灯亮=敌人退”，最优可能是“一直举灯”；
  - 如果“灯灭=敌人看不见我”，最优可能是“一直摸黑”；
  - 如果“掷灯=失去光源”，玩家可能从不掷；
  - 如果“点街灯=惊动敌人”，玩家可能从不点。
  brief 没有给出一个“必须灭灯/掷灯”的局面，H1 却要求 ≥4/5 主动灭灯/掷灯；这在设计上不自洽。

**L1 可行性**

- “复用现有灯笼/光照”只对一半：玩家腰间是 `_lamp_glow` 发光网格（`player.gd:206-220`），`_lamp_light: OmniLight3D` 声明但从未实例化；真正的光是街灯（`world.gd:920/942`）和 cam_key。要做“可携带光源”，需要新建 OmniLight/阴影/性能预算，不是复用。
- 5–7 天：如果只做“1 个可携带光 + 1 个敌人光敏 + 灯油条 + 1 个场景”，可能成立；但还要做掷灯/回收、致盲、Boss 整合、性能测试；5–7 天偏紧。
- 性能：C1 H4 要求 Intel HD 6000 ≥30 FPS；项目有 `probe_fps.gd`，但 portfolio 没有实际 `CHANGAN_FPS` 输出。黑暗场景 + 动态光 + 阴影是性能敏感项；没有基线就写 ≥30 FPS 是目标，不是验收。
- 可访问性：黑暗/迷路是 kill 信号，但 brief 没有亮度/对比度/音频提示/高亮轮廓的 fallback；对“动作轻中度”目标玩家，黑暗可能直接劝退。

**Playtest / kill**

- 样本：3 名动作核心 + 1 名氛围 + 1 名新人，偏向硬核；目标却是“轻中度”。核心玩家可能更喜欢“更黑更难”，不能代表目标受众（P2-3）。
- H1“≥4/5 至少一次灭灯/掷灯”太弱；玩家可能为了看动画试一次，不代表策略成立。
- H2“说得出灯油取舍”要求一个尚未定义的油经济；先定义，再测。
- H4“≥30 FPS”没有协议；应固定场景、分辨率、采样时长、min/avg/median、draw calls。
- kill“与现有 3 盏灯系统重复且没有新增决策”正好命中当前 brief：需要先证明新增决策，而不是把已有系统算成创新。

**IP/伦理/范围**

- 无直接 IP 复制；Alan Wake/Amnesia 是机制级参考。风险是 novelty 虚高，不是版权。
- 伦理/可访问性：黑暗不能只靠“更难”制造气氛；要有视觉/音频 fallback；不做血腥恐怖表达。
- 范围：不做新角色/剧情/开放街区/全局光照重写；brief 已经写了。若只做“灯油+光敏”，范围可控，但它已经不是“灯是武器”的新故事，而是现有灯系统的深化。

**Verdict：KILL（作为 top 3 创新）**

> C1 的当前 brief 不能进 L1：核心动词与现有 build 重复，3 个动词是功能堆叠，掷灯/灯油/光敏没有闭环，性能/可访问性没有证据。**保留**为现有灯系统的 P1 深化（例如给 Q 灯破加一个油条/光敏敌人），但不算 top 3 创新。
>
> 重新提交的最低条件：① 一个现有 build 做不到的 10 秒灰盒（比如“灭灯绕后→敌人失去目标→掷灯致盲→回收”的完整闭环）；② 一个核心动词 + 3 个支持动词以内；③ 油经济/掷灯回收/光敏状态机的最小数值；④ Intel HD 6000 的实测协议与结果；⑤ 亮度/对比度/音频 fallback。

**下一轮必须回答**

1. 现有 build 已经有哪些灯行为（Q 灯破、3 街灯、Boss 熄灯）？C1 的 delta 用一句话说是什么？
2. 核心动词是哪一个？“举/掷/灭”里哪一个是玩家每分钟重复做的？其余两个是否只是支持？
3. 掷灯后如何回收？灯油如何消耗/回复？给出最小数值，让“灭灯/掷灯”有代价。
4. 什么局面下“一直举灯”或“一直摸黑”不是最优？给一个必须灭灯/掷灯的具体遭遇。
5. 10 秒灰盒能展示什么现有 build 做不到的东西？如果展示不出来，为什么还要做？
