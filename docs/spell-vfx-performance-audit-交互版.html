结论先行

一页回答：审什么 / 怎么量 / 什么算过

业界一般不审“平均帧率”，而是审 最坏回合里的最坏一帧，并用三套证据交叉验证：帧时间分布（用户是否卡）、引擎计数器（卡在哪个阶段）、GPU / 资源证据（为什么卡）。回合制还多两个变量：可预知的施法序列，以及 倍速 / 跳过。

审什么

Cast → Turn → Battle → Soak

单次施法、回合窗口、整场、长局。任何异常先归到 cast，再归到 turn，最后才看整场。

怎么量

三套证据，不可替代

逐帧 frame_ms + 引擎计数器 + A/B 开关 / GPU 抓帧。只有计数器没有帧时间，会优化错对象。

什么算过

尾部分位 + 最坏帧 + 峰值资源

p95 / p99 / worst / hitch 全部在预算内；缺数据 = 不通过。阈值是政策值，首轮基线后校准。

03

三个优先验证场景

下一轮按 P1 → P2 → P3 执行

先用最小成本覆盖三种最坏形态：单体大招建立预算卡，AoE 多段压峰值，倍速连发抓生命周期错配。每个场景至少 3 次；前 2 次 cast 作为预热丢弃。

P1单体大招 · fire_spell

烈焰咒：弹道 + 命中

  • 青鸾对 boss_fox 施放 fire_spell；1×；原画。
  • 空场 5s → 施法 → 结束后 3s；重复 10 次，前 2 次作废。
  • 重启应用，重复 1 次，记录首放。
重点：弹道 72 粒子 + 命中 64/28 粒子；首放是否明显高于热态；暴击闪白是否叠加。
通过：首放 ≤ 50ms；热态 worst ≤ 16.7ms；无 >33.3ms 帧。
复制godot --path godot-battle --resolution 1920x1080 --print-fps \
  -s tools/smoke_hud_input.gd
P2AoE 多段 · thunder_storm

雷霆万钧：4 目标 + 全屏闪白

  • 对全体敌人施放 thunder_storm；1×；原画。
  • 重复 10 次；F2 卡通 5 次、水墨 5 次；1280×720 再 5 次。
  • 记录每次 cast 的峰值，不只看整场。
重点：4 个全屏闪白是否同帧叠加；4 个目标是否同帧触发 DamageCommand；音效请求是否超过 8 个（会出现抢占/截断）。
通过：draw calls 增量 ≤ +40；无 >33.3ms 帧；后处理 p95 增量 ≤ 3ms。
复制godot --path godot-battle --resolution 1280x720 --print-fps \
  -s tools/smoke_hud_input.gd
P3倍速连发 · sweep + 2× + skip

横扫千军：生命周期错配

  • 剑客对 3 个敌人施放 sweep；2×；连续 3 回合。
  • 第 2 回合在 cast 开始后 0.4s 触发「跳过本回合」。
  • 重复 5 组；每组做 1× 对照；skip 后 100ms/1s/3s 采样。
重点：playback_speed=1000 + generation 切换后，旧 Tween / 粒子 / Line2D 是否继续播放；闪白是否残留；顿帧是否把 2× 变成“更慢”。
通过：2× 并发 ≤ 1.5×；skip 后 1s 回到基线 ±10；孤儿 0 增长。
复制godot --path godot-battle --resolution 1920x1080 --print-fps \
  -s tools/smoke_hud_input.gd
